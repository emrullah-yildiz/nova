## Gap
There is no documented operational process for:
1. **Breach detection + notification.** No runbook for detecting a personal-data
   breach or for notifying the supervisory authority within 72h (Art. 33) and
   affected users (Art. 34).
2. **Backups & recovery.** The whole enterprise state is a single Neon snapshot
   blob; no documented backup cadence, restore test, or RPO/RTO. The decision log
   itself flags Neon storage limits but no backup plan exists.
3. **Dependency-vulnerability monitoring.** `npm audit` is a CI gate per
   ENGINEERING.md §4, but there is no documented policy for triage/SLA or for
   continuous monitoring (e.g. Dependabot/Snyk) between CI runs. (Note: a current
   `npm audit` reports 0 known vulnerabilities — good, but that is a point-in-time
   result, not a process.)

## Why it matters (user-rights impact)
Art. 32(1)(c) requires the ability to restore availability of personal data; Arts.
33–34 require breach notification on strict timelines. Without a written process
and a tested backup, a breach or data-loss event would be handled ad hoc and the
72h clock would likely be missed.

## Evidence
- No breach/incident/backup/recovery doc: `rg -li "breach|incident response|
  backup|recovery|72 hours"` over `docs` returns nothing relevant.
- Single-blob persistence: `worker/api.mjs:5-8` ("in-memory store with snapshot
  persistence … flushes on writes"); `server/db/neon-persistence.mjs`
  `writeSnapshot`.
- `npm audit --audit-level=low` → 0 vulnerabilities at time of audit (process,
  not point-in-time, is the gap).

## Recommended action / acceptance criteria
- PROCESS (needs human/ops owner): write an incident-response + breach-
  notification runbook covering detection, the 72h authority-notification path,
  and the user-notification trigger/template.
- PROCESS/CONFIG: define Neon backup/PITR cadence, run a documented restore test,
  and state RPO/RTO; ensure backup erasure is covered for SEC-004.
- PROCESS: adopt continuous dependency monitoring (Dependabot/Snyk) with a triage
  SLA, documented alongside the existing `npm audit` CI gate.
- Acceptance: a runbook exists with the 72h path; a restore has been tested and
  documented; dependency monitoring is enabled with an owner.
