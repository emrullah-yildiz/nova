## Gap
In `wrangler.toml`, both the production and the `env.dev` KV bindings — and both
`SESSION_KV` and `RATE_KV` within each — use the **same namespace id**
`2959d0665b324e53b58c2d1d5b752ffe`. That means the `nova-dev` Worker reads and
writes the same KV store as production: production session tokens
(`session:<hash>`), email-verification tokens (`emailverify:<hash>`), and rate
buckets all live in one namespace shared with dev. The deployment doc explicitly
says dev should use separate Neon data and separate KV namespaces "when
available," and the toml comment flags the ids as placeholders to replace.

## Why it matters (user-rights impact)
A dev deployment typically has looser controls and is where untested code runs. A
shared session/verification store means a bug or compromise in dev can read,
forge, or evict production users' sessions and verification tokens — a
confidentiality and account-takeover exposure for real users. Sharing rate
buckets also lets dev traffic exhaust production users' AI rate limits.

## Evidence
- `wrangler.toml` production `[[kv_namespaces]]` `SESSION_KV` and `RATE_KV` both
  `id = "2959d0665b324e53b58c2d1d5b752ffe"`.
- `wrangler.toml` `[[env.dev.kv_namespaces]]` `SESSION_KV` and `RATE_KV` — the
  same id `2959d0665b324e53b58c2d1d5b752ffe`.
- Comment in `wrangler.toml`: "Replace these IDs with dev-only namespaces when
  they are available."; `docs/architecture/deployment.md` ("Use a separate Neon
  database or schema for dev").

## Recommended action / acceptance criteria
- CONFIG: create distinct KV namespaces — at minimum a separate dev namespace,
  and ideally separate `SESSION_KV` vs `RATE_KV` namespaces — and update
  `wrangler.toml` so dev and prod never share session/verification/rate state.
- CONFIG: confirm dev uses a separate Neon database/schema (per deployment doc).
- Acceptance: `nova-dev` cannot read or write production session/verification KV
  keys; the toml shows distinct ids per environment.

## Resolution
`wrangler.toml` now binds `env.dev` (`nova-dev`) to its OWN dev-only KV
namespaces, fully separate from production:
- `env.dev` `SESSION_KV` → `7939bb17960c4de8a9e149c91c89300d`
- `env.dev` `RATE_KV` → `1a2391f8e5ea41c9855d0ff12d3c943d`
- production keeps its existing id `2959d0665b324e53b58c2d1d5b752ffe` (unchanged).

The two dev namespaces were created in Cloudflare (KV) by the maintainer and their
ids replace the former placeholders. `nova-dev` can no longer read or write
production session/verification/rate KV — the per-env ids are distinct (verified
in the Cloudflare dashboard Bindings view: dev no longer points at `nova-sessions`).

The separate-data half is also done: `nova-dev` is configured with its OWN Neon
database (a separate dev DB, set as the dev `NOVA_DATABASE_URL`), so dev shares
neither KV nor SQL state with production.

Documented in `docs/architecture/deployment.md` > "Dev KV namespaces (SEC-012)".
Acceptance met: distinct KV namespace ids per environment + separate dev database.
