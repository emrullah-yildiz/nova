## Gap
Every organization is created with `settings.dataRetentionDays: 365`, but that
value is **never read or enforced** anywhere in the code — `rg dataRetentionDays`
finds only the place it is set. Project versions, graph runs, AI request records,
and audit events accumulate with no pruning, no quota, and no retention
enforcement. The decision log ("Neon Stores Relational Data… Add project/version
quotas and retention rules before broad public usage") flags this as a known
pre-launch requirement.

## Why it matters (user-rights impact)
GDPR Art. 5(1)(c) (data minimization) and 5(1)(e) (storage limitation) require
that personal data not be kept longer than necessary. An advertised-but-unenforced
retention period is worse than none — it implies a limit that does not exist.
Unbounded growth also threatens the small Neon storage budget the decision log
warns about (an availability risk for all users).

## Evidence
- `src/enterprise/domain.mjs:68` `dataRetentionDays: 365` is set on every org and
  read nowhere (`rg -n dataRetentionDays src` → single match).
- `createProjectVersion` (`:1029`) pushes versions with no cap; `graphRuns`,
  `aiRequests`, `auditEvents` grow unbounded.
- decisions.md "Neon Stores Relational Data, Large Artifacts Belong Outside
  Postgres": "Add project/version quotas and retention rules before broad public
  usage."

## Recommended action / acceptance criteria
- CODE: enforce `dataRetentionDays` — prune (or anonymize) graph runs, AI request
  records, and audit events past the window (coordinate audit handling with
  SEC-006); cap version history per project (quota).
- POLICY: state the retention periods in the privacy policy (SEC-001).
- Acceptance: data older than the configured retention is pruned/anonymized on a
  schedule; version count per project is bounded; behavior is tested.
