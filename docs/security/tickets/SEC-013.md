## Gap
ARCHITECTURE.md states Connect/Revit writes are "approval-gated" and "every write
audited," and the server is the authority. In practice the approval check and the
audit call live in **browser code**: `revit-nodes.js` consults
`window.__revitWriteApproval` and then calls `recordHostAuditEvent` /
`recordHostOperation`. The audit record is created only because the client chooses
to call it, and the approval payload passed onward is a client-constructed
`{ approved: true, approvedBy: 'nova-user', ... }`. Nothing on the server (or in
the hub/add-in trust boundary) independently verifies that a write was actually
approved before it reaches Revit, or guarantees an audit row exists.

## Why it matters (user-rights impact)
A write to a live Revit model mutates the user's (or their client's) real project
data. If approval/audit are client-enforced, a bug, a tampered client, or a
direct call to the localhost hub can perform an unapproved, unlogged write —
contradicting the stated governance guarantee and removing the user's control
over destructive external operations. (`recordHostOperation` does correctly
require project write access — good — but it is invoked by the client, not a gate
the write must pass through.)

## Evidence
- `src/integrations/revit/revit-nodes.js:299-338` — approval via
  `window.__revitWriteApproval.requestWriteApproval`, audit via
  `recordHostAuditEvent`, then `setParameterValues(..., approval:{ approved:true,
  approvedBy:'nova-user', ... })` — all client-side; the approval object is
  client-fabricated.
- `src/enterprise/domain.mjs:926` `recordHostOperation` records an audit event
  but is only reached if the client calls the API; it does not gate the write.
- ARCHITECTURE.md §2/§4: "every write audited", "Server is the authority … Connect write
  approvals are enforced server-side" — not matched by the implementation.

## Recommended action / acceptance criteria
- CODE: move the write-approval gate to the trust boundary the write actually
  crosses (the hub/add-in pairing or a server-issued, single-use approval token),
  so a write cannot execute without a verifiable approval the client did not mint.
- CODE: make the audit record a precondition/side-effect of the write path on the
  authoritative side, not an optional client call.
- DOC: reconcile ARCHITECTURE.md's "enforced server-side / every write audited" claim
  with the implementation (update one to match the other).
- Acceptance: a write attempted without a valid approval token is rejected at the
  authoritative boundary and produces an audit record of the denial.

## Resolution

Resolved on `feat/sec-013-revit-write-gate`. The write-approval gate moved from
client-side/advisory code to the authoritative server boundary:

- **Server-issued, single-use token.** `EnterpriseStore.issueHostWriteApproval`
  (`src/enterprise/domain.mjs`) verifies project-write access, then mints a token
  with ≥256 bits of entropy bound to `{operation, projectId, graphVersion}` with a
  short TTL (default 2 min). Only the token *hash* is stored; the raw token is
  returned once. Issuance is audited as `host.write.approved`.
- **Audit as a precondition.** `EnterpriseStore.consumeHostWriteApproval` is the
  gate the write crosses: the token must be present, known, owned by the same
  caller, unconsumed, unexpired, and scope-matching, and project-write access is
  re-checked at consume time. The token is burned (single-use) before recording.
  Every call audits — an accepted write as `host.operation`, a refused one as
  `host.write.denied` with a structured `reason`. There is no path where a write
  is accepted without an audit row, and no path where a denial is silent.
- **End-to-end wiring (the live runtime path).** The domain functions above are
  now actually reachable at runtime — the previously-inert pieces are wired:
  - `POST /api/host-write-approvals` (`src/enterprise/api-dispatch.mjs`) exposes
    `issueHostWriteApproval` (returns the one-time raw token + `approvalId`).
  - `POST /api/host-operations` is now `handleRecordHostOperation`, which is the
    **authoritative consumer**: it requires `body.token` and calls
    `consumeHostWriteApproval` (burn + audit-as-precondition). The old audit-only
    `recordHostOperation` is no longer routable, so there is no path that records
    a reported write without consuming a token.
  - `issueWriteToken` (`src/integrations/connect/revit-write-approval.js`,
    exposed on `window.__revitWriteApproval`) requests the server token via the
    cloud client (`NovaCloudClient.issueHostWriteApproval`); signed-out it
    degrades to a clearly-marked **local token** (never server-consumed/audited)
    so the local pilot stays usable offline.
  - After a write lands, `RevitBridge` reports it via `recordHostAuditEvent`
    (→ `recordHostOperation` → `POST /api/host-operations`), carrying the token —
    this is what triggers the authoritative consume.
- **No client-minted approval.** `RevitBridge` (`src/integrations/revit/revit-nodes.js`)
  runs the UX consent step and then requests the server token, forwarding
  `payload.approval = { token, approvalId, operation, graphVersion }`. `client.js`
  `normalizeWriteApproval` now **preserves exactly those fields and strips
  everything else** — the old client-fabricated `{ approved: true, approvedBy:
  'nova-user' }` boolean (and its `{approved:true}` default) is gone from the
  wire; without a server token, the write is refused client-side too.
- **Add-in defense in depth.** `NovaHostClient` (`integrations/revit-addin/`)
  refuses any write whose `payload.approval.token` is missing/empty
  (`HasWriteApprovalToken`), replacing the forgeable `approval.approved` boolean
  check on `geometry.create`, `geometry.place`, and `parameter.set`.
- **Docs reconciled.** `docs/architecture/revit-connect.md` documents the real
  issue→carry→consume flow (the two routes), the token format/verification, and
  that authoritative enforcement requires the enterprise backend (hub = transport,
  add-in = presence-check). ARCHITECTURE.md §4's "enforced server-side" claim now names
  both routes and matches the implementation.

Tests:
- `tests/sec-013-write-gate-wiring.test.js` — exercises the REAL wiring through
  the dispatcher: the issue route mints a token; a reported write with a valid
  token consumes it + records `host.operation`; a report with no/forged/replayed/
  scope-mismatched token is rejected **at the server boundary (403)** and audited
  as `host.write.denied`; plus `client.js` token preservation (no `{approved:true}`)
  and `issueWriteToken` server wiring + graceful local degrade + the local-token
  no-report rule.
- `tests/sec-013-revit-write-gate.test.js` (kept) — domain issue/consume in
  isolation (missing/forged/expired/replayed/scope/owner-mismatch denials audited).
- `tests/sec-013-revit-nodes-token.test.js` — RevitBridge forwards the server
  token, blocks when no issuer/consent, gates `sendGeometry`.
