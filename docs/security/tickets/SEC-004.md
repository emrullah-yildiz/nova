## Gap
`DELETE /api/me` calls `deleteUserAccount`, which removes the user row, personal
orgs/projects, runs, artifacts, share links, AI requests, and connector sessions
from the in-memory store. But several PII-bearing artifacts are **not** purged:
1. **KV session tokens.** Only the *active* slot's session is cleared from KV on
   deletion (`worker/api.mjs` DELETE branch clears `clearSlotCookie(active)` and
   no `session:` KV delete). Any other valid `session:<hash>` for that user in
   `SESSION_KV` survives until natural TTL — the deleted user can keep making
   authenticated calls from another device/slot.
2. **Email-verification tokens** keyed `emailverify:<hash>` in KV are never
   removed on deletion.
3. **Audit events** retain `userId`, login events, and the user's email in
   metadata; `account.deleted` is appended but prior events (incl. any with PII)
   are kept indefinitely (see SEC-006).
4. **Backups / Neon point-in-time history** are out of scope of the in-memory
   purge entirely (no documented backup-erasure process — see SEC-009).

## Why it matters (user-rights impact)
Art. 17 requires erasure of personal data "without undue delay." A session token
that still authenticates a deleted account is both an erasure failure and an
access-control failure (the account is gone but the credential works). Leftover
verification tokens and audit PII mean the user's data is not actually removed.

## Evidence
- `src/enterprise/domain.mjs:210` `deleteUserAccount` — no iteration over
  `stateStore` session/verification keys (it has no index of the user's session
  hashes to delete).
- `worker/api.mjs:234-247` — on DELETE `/api/me` only the active slot cookie is
  cleared; `handleLogout`'s `dropKv('session:'+hashToken(token))` pattern is NOT
  applied across the deleted user's other slots, and no `emailverify:` cleanup.
- `worker/api.mjs:263-265` shows the KV session key format that deletion omits.

## Recommended action / acceptance criteria
- CODE: on account deletion, enumerate and delete every `nova_session_<slot>`
  the request carries for that user from KV (mirror `handleLogout` scope:'all'
  but scoped to the deleted user), and clear all slot cookies, not just active.
- CODE: delete the user's outstanding `emailverify:` KV tokens (store an index
  of issued token keys per user, or accept they expire by TTL and document it).
- CODE/PROCESS: decide audit retention vs erasure (coordinate with SEC-006) —
  e.g. anonymize `userId`/email in retained audit rows after deletion.
- PROCESS: document backup/PITR erasure (SEC-009).
- Acceptance: after `DELETE /api/me`, no KV `session:`/`emailverify:` key for the
  user authenticates or resolves; a test asserts a pre-deletion token is rejected.

## References
GDPR Art. 17; `src/enterprise/domain.mjs` `deleteUserAccount`; `worker/api.mjs`;
`worker/cookies.mjs`.

## Resolution
Resolved on branch `fix/sec-004-account-deletion-purge` (2026-06-04).

- **Session/verify-token enumeration.** `EnterpriseStore` now keeps a per-user
  index, `userKvKeys: Map<userId, Set<key>>`, populated whenever a
  `session:<hash>` (in `createAuthSessionAsync`) or `emailverify:<hash>` (in
  `createEmailVerificationTokenAsync`) key is minted, and pruned when an
  email-verify token is consumed. `deleteUserAccount` returns
  `{ ok, deletedProjectCount, kvKeys }` — `kvKeys` is the full set of the
  deleted user's session/verify KV keys. KV has no prefix scan, so this index is
  the enumeration mechanism the ticket asked for.
- **DELETE /api/me purge (`worker/api.mjs`).** The handler resolves this
  browser's slot→token map and the active (to-be-deleted) user's id **before**
  dispatch runs — dispatch deletes the user row, after which the cookies can no
  longer be authenticated (`requireUser` throws 404). Using that captured
  snapshot, after deletion the branch (a) `dropKv()`s every key in
  `payload.kvKeys`, and (b) derives `session:<hash>` from the **captured** slot
  cookies for **every** slot owned by the deleted user — not just the active
  slot — and drops those too. This double-covers the access-control bug: the
  same-browser sessions (cookie-derived, always purged) and any other-device
  sessions the store's in-memory index still knows about (via `kvKeys`).
- **All slot cookies cleared.** Every slot owned by the deleted user is cleared
  (plus any slot whose token failed auth), the active pointer is re-pointed to a
  surviving account or cleared, and `clearAllSlotCookies()` was added to
  `worker/cookies.mjs` (also now used by logout scope:'all').
- **Audit anonymization.** Retained in-memory audit rows for the user have their
  `userId`/`targetId` blanked and any email/userId values in `metadata` stripped;
  the `account.deleted` record itself carries no `userId`. Durable (Neon) audit
  rows are append-only by id (snapshot writes `ON CONFLICT DO NOTHING`), so
  durable-store anonymization remains a retention process tracked in **SEC-006**.
- **emailverify cleanup.** KV `emailverify:` keys are dropped via the returned
  `kvKeys`; the node/dev in-memory `emailVerifications` map is swept by userId.
- **Cascade verified.** Projects (personal-org), versions, members (incl.
  cross-org project membership removal), runs, artifacts, share links, AI
  requests, background jobs, and connector sessions were already purged by
  `deleteUserAccount` and are exercised by the existing domain tests.

**Known limit (documented):** `userKvKeys` is in-memory and not persisted to
Neon (no snapshot column), so after a cold isolate restart it only holds tokens
minted since boot. The security-critical case — the deleting browser's own live
session(s) — is **always** purged: those `session:<hash>` keys are derived from
the request's slot cookies captured *before* deletion, independent of the
in-memory index. What can still fall back to natural TTL expiry (sessions ~8h,
email-verify 24h) is an OTHER-device session for the deleted user when the store
is on a cold isolate (so its index doesn't list that key and the deleting
browser doesn't carry that device's cookie). That residual is tracked with
SEC-006/SEC-009. Durable backup/PITR erasure is out of scope here (**SEC-009**).

**Tests:** `tests/account-deletion-purge.test.js` — a pre-deletion token from
each of two devices is rejected after deletion (store level), audit PII is
anonymized, the in-memory verify map is cleared, and a full Worker
signup→verify→login→`DELETE /api/me` flow proves the slot cookie is cleared and
the captured `session:` KV key no longer resolves. Two further Worker tests
cover the multi-account and cold-isolate paths: (1) with TWO distinct users
signed into two slots, deleting one leaves the OTHER user's slot cookie untouched
and its `session:<hash>` key still authenticating (no over-deletion); (2) with
the deleted user's live session present via cookie but absent from the store's
`userKvKeys` index (simulating a cold isolate), the active `session:` key is
still dropped via the captured-token path (the F-001 fix), while an other-device
key the index never saw is documented to fall back to TTL.
