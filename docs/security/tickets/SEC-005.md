## Gap
The only rate limiter in the deployed stack is the per-IP AI-proxy limiter
(`worker/index.mjs` `checkRate`). The authentication routes — `/api/auth/login`,
`/api/me/password`, `/api/auth/verify`, `/api/auth/resend-verification`,
`/api/auth/signup` — have **no rate limiting or lockout**. An attacker can submit
unlimited password guesses against `handleLogin` (PBKDF2 verify per attempt) and
unlimited verification-token guesses, bounded only by network speed.

## Why it matters (user-rights impact)
Art. 32 requires appropriate security of processing. Unthrottled login is the
textbook credential-stuffing / brute-force exposure (OWASP ASVS V2.2.1: anti-
automation on authentication). Although login uses a single generic error to
resist enumeration (good), an attacker can still mount online password attacks
and abuse the email-sending path (`resend-verification`) for spam/cost.

## Evidence
- `src/enterprise/api-dispatch.mjs:409` `handleLogin` — verifies password, no
  attempt counter / backoff.
- `src/enterprise/api-dispatch.mjs:312` `handleChangePassword`,
  `:256` `handleVerifyEmail`, `:270` `handleResendVerification` — no throttle.
- `worker/index.mjs` `checkRate` (lines 151–160) is invoked only inside the
  `/api/proxy/chat` handler; the `/api/*` enterprise dispatch path
  (`handleEnterpriseApi`) applies no limiter.

## Recommended action / acceptance criteria
- CODE: add a per-IP and per-account rate limit + exponential backoff/lockout to
  the auth routes, backed by the existing `RATE_KV` (reuse the `checkRate`
  pattern with auth-specific keys/limits). Cap `resend-verification` and signup
  per IP/email.
- CODE: add a test asserting repeated failed logins are throttled (429/lockout).
- Acceptance: N failed logins within a window are rejected before reaching
  PBKDF2 verify; verification-token guessing is rate-limited.
