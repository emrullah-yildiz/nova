## Gap
User personal data flows to multiple third parties with **no disclosed Data
Processing Agreement, no Standard Contractual Clauses / transfer mechanism, no
user disclosure, and unknown data residency**:
- **AI providers (Groq, Google Gemini)** receive the user's chat prompts AND a
  snapshot of their project graph, via the shared free-tier proxy and via BYOK
  direct calls.
- **Resend** receives account/invite email addresses.
- **Cloudflare** hosts the Worker, sessions (KV), and rate-limit data.
- **Neon (Postgres)** stores all relational data including the full enterprise
  snapshot.
None of these are named to the user, and the EU-personal-data residency of each
(especially Neon and Cloudflare KV/DO region) is unverified.

## Why it matters (user-rights impact)
GDPR Art. 13(1)(e) requires disclosing recipients; Art. 28 requires a written
processor contract (DPA) with every processor; Arts. 44–49 require a valid
mechanism (e.g. SCCs / adequacy) for transfers outside the EEA. Groq and Gemini
in particular receive substantive user content (prompts + graph context), so an
undisclosed/unprotected transfer here is a direct exposure of user data. Data
residency in Neon/Cloudflare is **UNKNOWN** and must not be assumed compliant.

## Evidence
- AI proxy forwards prompts to Groq/Gemini: `api/proxy/chat.mjs` `PROVIDERS`
  (lines 11–48), `forwardBody`; Worker `worker/index.mjs` `app.post('/api/proxy/chat')`.
- Graph context is injected into the prompt: `src/ai/graph-context.js` (decision
  log "AI Assistant Sees A Live Graph Snapshot").
- BYOK direct-to-provider calls: `src/ai/gpt-client.js` `apiUrl`
  `https://api.groq.com/...`, `https://generativelanguage.googleapis.com/...`.
- Email: `server/email/resend.mjs` (`createEmailService`).
- DB: `server/db/neon-persistence.mjs`; hosting `wrangler.toml`. Neon region and
  Cloudflare KV/DO placement are not pinned anywhere in the repo.

## Recommended action / acceptance criteria
- LEGAL/PROCESS (needs counsel): execute and file a DPA with each sub-processor
  (Groq, Google, Resend, Cloudflare, Neon); confirm the transfer mechanism (SCCs
  / adequacy) for each; record each in a sub-processor register. Mark each row
  `UNKNOWN — needs human input` until verified.
- PROCESS/CONFIG: determine and document the Neon region and the Cloudflare
  KV/DO/Worker data region for EU personal data; pin region in provisioning docs.
- POLICY: list these sub-processors in the privacy policy (SEC-001).
- This is an engineering audit, not legal advice — the existence/adequacy of each
  DPA is **UNKNOWN — needs human input**.

## Progress (2026-06-04)
Sub-processor list + data map + international-transfer section drafted in
`docs/legal/data-handling.md`. Confirmed with the maintainer: there is **no free-tier
AI** (no Nova-held Groq/Gemini key), so the actual Nova sub-processors are **Cloudflare**,
**Neon (EU/Ireland)**, **Google (sign-in/OIDC only)**, and **Resend** (email sending
is configured/active). AI providers are BYOK-only (browser→provider direct) and are therefore
**not** Nova sub-processors. REMAINING (legal/process): execute & file signed DPAs/SCCs
with those four, confirm per-provider transfer mechanism, publish, and set up a
notify-users-on-change process. Status: in-progress.

## Resolution (2026-06-04)
**Resolved.** The four actual sub-processors — Cloudflare, Neon (EU/Ireland), Google
(sign-in/OIDC only), Resend — are disclosed in `docs/legal/data-handling.md` §2 with a
per-provider **DPA / SCCs** column, and in the published Privacy Policy. Each provider's
DPA (with its SCCs for transfers) is **incorporated into its standard terms**, which
apply to the account — confirmed as the basis with the maintainer. Data residency is
documented (primary store Neon = EU/Ireland; Cloudflare edge global; Google/Resend US
for sign-in/email). AI providers are NOT sub-processors (BYOK, browser→provider direct).
Accountability follow-through (owner): keep each provider's current DPA URL/acceptance
on file so it can be produced on request.
