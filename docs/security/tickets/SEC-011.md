## Gap
`parseXLSX`/`parseCSV` parse uploaded files (a recently-added feature) with the
SheetJS `xlsx` library and a hand-written CSV tokenizer, but apply **no upper
bound** on input size, number of sheets, rows, columns, or total cells. A
maliciously crafted or simply very large workbook (e.g. a "zip bomb"-style sheet
declaring an enormous used range, or a multi-hundred-MB CSV) can exhaust memory
or hang the tab.

## Why it matters (user-rights impact)
Parsing runs client-side on untrusted input. While the module commendably defends
against prototype pollution (null-prototype rows for `__proto__`/`constructor`
headers — good), it does not defend against resource exhaustion. A user opening a
hostile file (or a shared project that references one) can lose their unsaved
work to a frozen/crashed tab — an availability harm. SheetJS has a history of
parser CVEs (prototype pollution, ReDoS), so input must be bounded defensively.

## Evidence
- `src/data/spreadsheet-parse.js:329` `parseXLSX` calls `XLSX.read(...)` and
  `XLSX.utils.sheet_to_json(... header:1 ...)` with no size/dimension guard.
- `:156` `parseCSV` / `:68` `tokenizeCSV` iterate the whole string with no length
  cap.
- `src/ui/file-control.js` reads the file (no size check found there either).
- Dependency pinned: `xlsx@0.20.3` (current `npm audit` clean, but parser
  hardening is still warranted given the library's CVE history).

## Recommended action / acceptance criteria
- CODE: enforce a max upload byte size in `src/ui/file-control.js` before reading
  the file; reject oversized files with a clear message.
- CODE: cap rows/columns/total cells in `parseXLSX`/`parseCSV` (e.g. refuse > N
  rows or > M cells), and cap the input string length in `tokenizeCSV`.
- CODE: add tests for the limits (oversized file rejected; pathological sheet
  bounded).
- Acceptance: a file above the configured limits is rejected before it can hang
  the tab; limits are documented.
