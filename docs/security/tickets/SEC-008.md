## Gap
BYOK provider keys are persisted client-side in plaintext localStorage
(`nodeflow_key_groq`, `nodeflow_key_openrouter`, and similar). localStorage is
readable by any JavaScript executing in the origin, so a single XSS, a
compromised dependency, or a malicious browser extension can exfiltrate the
user's API keys. (The server-synced copy IS encrypted at rest — SEC notes that
positively — but the local working copy is not protected.)

## Why it matters (user-rights impact)
The key is the user's own paid credential; its theft lets an attacker run up
charges or access the user's AI account. Storing long-lived secrets in
localStorage is an OWASP-flagged anti-pattern (ASVS V8 / sensitive data; the
localStorage-secret risk). The blast radius of any XSS in Nova is amplified to
"steals every user's AI keys."

## Evidence
- `src/ai/gpt-client.js:1132` `localStorage.getItem('nodeflow_key_groq')`,
  `:1138` `localStorage.getItem('nodeflow_key_openrouter')` — plaintext read;
  keys are written to localStorage on save.
- Server-side encrypted alternative exists (`handlePutAiSettings` +
  `server/auth/webcrypto.mjs` AES-GCM) but the client still keeps a plaintext
  local copy for direct provider calls.

## Recommended action / acceptance criteria
- CODE: prefer routing BYOK calls so the raw key is not persisted in localStorage
  — e.g. keep the key only in memory for the session, or rely on the
  server-side encrypted store + proxy. If a local copy is unavoidable for direct
  calls, minimize its lifetime (session-only) and document the residual risk.
- CODE: provide a clear "disconnect/clear keys" control that wipes all
  `nodeflow_key_*` entries.
- This raises the importance of XSS hardening (see SEC-010).
- Acceptance: a fresh load does not expose a long-lived plaintext key in
  localStorage by default; clearing keys removes every provider entry.

## References
OWASP ASVS V8 (data protection); `src/ai/gpt-client.js`;
`server/auth/webcrypto.mjs` (the encrypted server path that already exists).

## Resolution
Fixed in `fix/sec-008-byok-key-storage`.

**Storage approach (no long-lived plaintext key by default).** All AI-credential
prefs route through a swappable backend (`GPTClient._prefs`) rather than touching
`localStorage` directly:
- Anonymous users → `sessionStorage`, which is cleared when the tab/browser
  closes (with an in-memory fallback for locked-down browsers).
- Signed-in users → an in-memory cache hydrated from the account and synced to
  the existing **encrypted** server store (`handlePutAiSettings` /
  `aiSettingsEncrypted`, AES-GCM via `server/auth/webcrypto.mjs`).
A one-time `_migrateLegacyLocalPrefs()` lifts any legacy keys out of
`localStorage` into the session backend and then **purges** them, so a fresh load
exposes no persistent plaintext BYOK key. This routing was already in place; the
remaining gap was that `switchToFreeModel()` still read fallback keys with raw
`localStorage.getItem('nodeflow_key_groq' / '…_openrouter')`. Those two reads now
go through `_prefGet`, so the rate-limit fallback no longer depends on (or
re-exposes) a plaintext `localStorage` copy.

**Disconnect / clear-keys action.** Added `GPTClient.clearAllKeys()`, which removes
every `nodeflow_key_<provider>` entry plus the legacy `nodeflow_openai_key` alias
from the active backend, and also calls `localStorage.removeItem(...)` for each as
a belt-and-suspenders scrub of any stale plaintext copy left by a pre-fix build.
For signed-in users the in-memory backend's `remove()` schedules a PUT, so the
empty key-set clears the encrypted server store too. A red **"Disconnect / Clear
Keys"** button in Settings (`SettingsDialog.disconnect()`) wires it to the UI,
clears the visible input, and refreshes the chat status/gate.

**Tests.** `tests/sec-008-byok-key-storage.test.js` asserts: keys are not written
to `localStorage` in plaintext by default; a fresh load exposes no persistent
key; `clearAllKeys()` wipes every provider entry + legacy alias; `clearAllKeys()`
scrubs stale plaintext `localStorage` copies; `switchToFreeModel()` reads
fallbacks from the backend (not `localStorage`); and the no-op/return-count
behavior. Full suite green (`vitest run`: 1557 passed, 1 skipped).

Residual risk: while a key is in use during a session it lives in memory /
`sessionStorage` and is therefore reachable by script running in the origin — this
is inherent to making direct browser→provider BYOK calls and is now minimized to
session lifetime. Further reduction depends on XSS hardening (SEC-010).
