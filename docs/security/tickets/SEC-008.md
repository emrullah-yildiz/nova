## Gap
BYOK provider keys are persisted client-side in plaintext localStorage
(`nodeflow_key_groq`, `nodeflow_key_openrouter`, and similar). localStorage is
readable by any JavaScript executing in the origin, so a single XSS, a
compromised dependency, or a malicious browser extension can exfiltrate the
user's API keys. (The server-synced copy IS encrypted at rest — SEC notes that
positively — but the local working copy is not protected.)

## Why it matters (user-rights impact)
The key is the user's own paid credential; its theft lets an attacker run up
charges or access the user's AI account. Storing long-lived secrets in
localStorage is an OWASP-flagged anti-pattern (ASVS V8 / sensitive data; the
localStorage-secret risk). The blast radius of any XSS in Nova is amplified to
"steals every user's AI keys."

## Evidence
- `src/ai/gpt-client.js:1132` `localStorage.getItem('nodeflow_key_groq')`,
  `:1138` `localStorage.getItem('nodeflow_key_openrouter')` — plaintext read;
  keys are written to localStorage on save.
- Server-side encrypted alternative exists (`handlePutAiSettings` +
  `server/auth/webcrypto.mjs` AES-GCM) but the client still keeps a plaintext
  local copy for direct provider calls.

## Recommended action / acceptance criteria
- CODE: prefer routing BYOK calls so the raw key is not persisted in localStorage
  — e.g. keep the key only in memory for the session, or rely on the
  server-side encrypted store + proxy. If a local copy is unavoidable for direct
  calls, minimize its lifetime (session-only) and document the residual risk.
- CODE: provide a clear "disconnect/clear keys" control that wipes all
  `nodeflow_key_*` entries.
- This raises the importance of XSS hardening (see SEC-010).
- Acceptance: a fresh load does not expose a long-lived plaintext key in
  localStorage by default; clearing keys removes every provider entry.
